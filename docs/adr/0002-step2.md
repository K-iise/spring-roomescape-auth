## 1. JWT 토큰 기반 인증으로 전환

- 상태: 채택 (Accepted) — 1단계 ADR [결정 1. 세션 기반 인증 채택](./0001-step1.md#1-세션-기반-인증-채택)을 대체한다.
- 일자: 2026-06-17

### 맥락 (Context)

1단계에서는 단일 서버 환경을 전제로 세션 기반 인증을 채택했고, 그 결정의
재검토 조건으로 *"외부 클라이언트(모바일 등)에 인증을 개방해야 하는 요구가 생기면
토큰 기반 인증으로의 전환을 다시 검토한다"* 를 명시해 두었다. 2단계에서 웹뿐 아니라
네이티브 앱(모바일) 클라이언트까지 동일한 인증을 사용해야 하는 요구가 생기면서
이 조건이 현실화되었다.

다시 두 가지 선택지를 비교한다.

- **세션/쿠키 방식**: 서버가 세션 상태를 보관하고, 클라이언트는 세션 ID 쿠키를
  들고 다닌다. 브라우저는 쿠키를 자동으로 주고받는다.
- **JWT 토큰 방식**: 서버가 서명된 토큰을 발급하고 요청마다 검증한다. 토큰은
  `Authorization` 헤더(Bearer)에 직접 담아 전달하며, 서버는 인증 상태를 보관하지
  않는다(무상태, Stateless).

### 결정 (Decision)

**JWT 토큰 방식을 채택한다.** 토큰은 `Authorization: Bearer <token>` 헤더로 전달하며,
웹/모바일이 동일한 검증 로직을 재사용한다.

이유는 다음과 같다.

1. **클라이언트 종류에 무관한 일관성**: 순수 네이티브 앱(Retrofit, URLSession 등으로
   직접 HTTP 통신)은 쿠키 저장소가 없어 세션 방식이 자동으로 동작하지 않는다. 토큰
   방식은 `Authorization` 헤더에 직접 담으면 되므로 웹/모바일 클라이언트 종류에
   상관없이 일관되게 사용할 수 있다.
2. **무상태(Stateless)로 인한 확장 용이성**: 서버가 인증 상태를 저장하지 않아도
   되므로, 서버를 다중 인스턴스로 확장할 때 세션 공유 문제(스티키 세션, 외부 세션
   저장소 등)가 발생하지 않는다.

### 결과 (Consequences)

긍정적

- 웹/모바일 등 클라이언트 종류와 무관하게 동일한 방식으로 인증을 처리한다.
- 서버가 인증 상태를 보관하지 않으므로 세션 저장소가 불필요하고, 수평 확장 시
  세션 공유 문제가 사라진다.

부정적 / 트레이드오프

- 세션 방식은 로그아웃 시 서버에서 세션을 즉시 무효화할 수 있지만, 토큰 방식은
  클라이언트가 로컬 스토리지에서 토큰을 제거하는 방식이므로 **토큰 자체의 유효성은
  만료 시간까지 살아있다.**
- 따라서 토큰이 탈취된 경우, **만료 전까지 서버에서 막을 방법이 없다.**

재검토 조건

- 로그아웃 즉시 차단·강제 로그아웃·탈취 대응 등 "발급한 토큰을 만료 전에 무효화"해야
  하는 요구가 생기면, refresh 토큰 도입과 서버측 폐기 수단(블랙리스트, tokenVersion 등)을
  검토한다. 이는 일부 상태를 다시 도입하는 절충이 된다.

## 2. 토큰 전달 위치 — Authorization 헤더(Bearer)

- 상태: 채택 (Accepted)
- 일자: 2026-06-17

### 맥락 (Context)

[결정 1](#1-jwt-토큰-기반-인증으로-전환)에서 JWT 토큰 방식을 채택했다. 그렇다면
발급한 토큰을 클라이언트가 서버로 **어디에 담아 전달할지**를 정해야 한다. 크게 두
가지 선택지가 있다.

- **쿠키**: 서버가 `Set-Cookie`로 토큰을 내려주고, 브라우저가 이후 요청에 자동으로
  실어 보낸다.
- **Authorization 헤더(Bearer)**: 클라이언트가 `Authorization: Bearer <token>`
  형태로 직접 헤더에 담아 전송한다.

### 결정 (Decision)

**Authorization 헤더(Bearer 토큰)로 전달한다.**

이유는 다음과 같다.

1. **클라이언트 종류에 무관한 일관성**: 네이티브 앱은 쿠키 저장소가 없기 때문에
   쿠키 방식으로는 토큰을 전달할 수 없다. Authorization 헤더 방식은 클라이언트가
   직접 담아서 전송하므로 웹/모바일 상관없이 동일하게 사용할 수 있다.
2. **CSRF 방어**: 쿠키는 브라우저가 자동으로 전송하는 특성 때문에 CSRF 공격에
   취약하지만, Authorization 헤더는 클라이언트가 직접 담아야 하므로 CSRF 공격을
   방어할 수 있다.

### 결과 (Consequences)

긍정적

- 웹/모바일 등 클라이언트 종류와 무관하게 동일한 방식으로 토큰을 전달한다.
- 브라우저의 쿠키 자동 전송에 기대지 않으므로 CSRF 공격 표면이 줄어든다.

부정적 / 트레이드오프

- 쿠키와 달리 클라이언트가 직접 Authorization 헤더에 토큰을 담아서 전송해야 한다.
  브라우저처럼 자동으로 처리되지 않으므로, 토큰 저장·헤더 첨부에 대한 클라이언트
  구현이 필요하다.

## 3. 웹/모바일 공통 인증 처리 — 인터셉터 + ArgumentResolver

- 상태: 채택 (Accepted) — 1단계 ADR [결정 2. 공통 처리 방식 — 인터셉터 + ArgumentResolver](./0001-step1.md#2-공통-처리-방식--인터셉터--argumentresolver)를 토큰 기반으로 잇는다.
- 일자: 2026-06-17

### 맥락 (Context)

토큰 기반 인증([결정 1](#1-jwt-토큰-기반-인증으로-전환))을 웹과 모바일이 함께 사용한다.
이때 토큰 검증과 로그인 사용자 식별을 **클라이언트 종류별로 따로 처리할지**, 아니면
**하나의 공통 로직으로 통합할지** 정해야 한다.

- **클라이언트별 어댑터**: 웹/모바일 인증을 각각 따로 구현한다.
- **공통 검증 로직 재사용**: `AuthInterceptor`와 `HandlerMethodArgumentResolver`로
  인증을 공통화하여 클라이언트 종류와 무관하게 동일한 로직을 재사용한다.

### 결정 (Decision)

**공통 검증 로직(AuthInterceptor + ArgumentResolver)을 재사용한다.**

- `AuthInterceptor`가 `Authorization` 헤더에서 토큰을 추출(`AuthorizationExtractor`)해
  검증(`JwtTokenProvider`)하고, 미인증·무효 토큰을 `UnauthorizedException`(401)으로
  차단한다.
- `LoginMemberArgumentResolver`가 같은 방식으로 토큰을 검증한 뒤 `AuthService.findById`로
  회원을 조회하여, 컨트롤러에 `@Login LoginMember`(회원 식별자·이름) 파라미터로 주입한다.
- 그 결과 컨트롤러는 웹/모바일 구분 없이 `@Login LoginMember member` 하나로 동일하게
  로그인 사용자를 받아 처리한다.

클라이언트별로 인증 로직을 따로 구현하면 코드 중복이 발생하고 컨트롤러가 복잡해지므로,
공통 로직으로 통합하는 방식을 선택했다. (검증은 헤더 기반이라 서블릿 필터 없이도 Spring
MVC 계층에서 처리되며, 인증 실패가 `@RestControllerAdvice`를 거쳐 일관된 401 JSON으로
변환된다.)

### 결과 (Consequences)

긍정적

- 인증 로직이 한곳(인터셉터·리졸버)에 모여 웹/모바일 클라이언트마다 중복되지 않는다.
- 컨트롤러는 클라이언트 종류를 의식하지 않고 `@Login LoginMember`만으로 사용자를 받는다.

부정적 / 트레이드오프

- 웹과 모바일의 인증 실패 응답을 다르게 처리하고 싶은 경우(예: 웹은 로그인 페이지로
  리다이렉트, 모바일은 401 JSON), 동일 로직을 재사용하는 구조에서는 클라이언트별로
  다른 응답을 내려주기 까다롭다. 현재는 양쪽 모두 `UnauthorizedException` → **401 JSON**으로
  통일해 응답한다.

## 4. 만료·로그아웃 처리 — 토큰 만료에 위임

- 상태: 채택 (Accepted) — [결정 1](#1-jwt-토큰-기반-인증으로-전환)의 무상태 특성에 따른 후속 결정.
- 일자: 2026-06-17

### 맥락 (Context)

JWT는 무상태이므로 서버가 발급한 토큰의 생사를 직접 관리하지 않는다. 그렇다면
로그아웃과 토큰 무효화를 어떻게 다룰지 정해야 한다.

- **토큰 만료에 위임**: 서버는 무효화 저장소를 두지 않고, 로그아웃은 클라이언트가
  로컬 스토리지에서 토큰을 제거하는 것으로 처리한다.
- **accessToken + refreshToken**: 짧은 수명의 accessToken과 서버가 보관하는
  refreshToken을 분리한다. 로그아웃·강제 만료 시 서버에서 refreshToken을 폐기한다.

### 결정 (Decision)

**토큰 만료에 위임한다.** 로그아웃은 클라이언트가 로컬 스토리지에서 토큰을 제거하는
방식으로 처리하며, 서버에는 별도의 로그아웃 엔드포인트나 토큰 무효화 저장소를 두지
않는다.

이유는 다음과 같다.

1. 현재 미션 수준에서 accessToken + refreshToken 방식을 도입하는 것은 과도한
   복잡도라고 판단했다.
2. 토큰 만료 시간을 짧게 설정하는 것으로 보안 위험을 최소화할 수 있다.
   (현재 만료 시간은 `jwt.expiration-ms`로 설정한다.)

### 결과 (Consequences)

긍정적

- 서버에 무효화 저장소·로그아웃 처리 로직이 없어 구조가 단순하고 무상태성이 유지된다.

부정적 / 트레이드오프

- 로그아웃 시 클라이언트에서 토큰을 제거하더라도 토큰 자체의 유효성은 만료 시간까지
  살아있다.
- 토큰이 탈취된 경우 서버에서 즉시 막을 방법이 없다.

재검토 조건

- 즉시 무효화·강제 로그아웃·탈취 대응이 필요해지면 [결정 1](#1-jwt-토큰-기반-인증으로-전환)의
  재검토 조건과 같이 accessToken + refreshToken 도입과 서버측 폐기 수단을 검토한다.

## 5. 인증 실패 응답 — 웹/모바일 동일 401

- 상태: 채택 (Accepted) — [결정 3](#3-웹모바일-공통-인증-처리--인터셉터--argumentresolver)의 공통 처리 방침을 응답까지 확장한다.
- 일자: 2026-06-17

### 맥락 (Context)

인증되지 않은 요청이 인증이 필요한 API에 접근했을 때, 서버가 어떤 응답을 내려줄지
정해야 한다.

- **웹/모바일 동일 응답**: 클라이언트 종류와 무관하게 동일하게 `401 Unauthorized`
  (일관된 JSON 형식)로 응답한다.
- **웹/모바일 분리**: 웹은 `302`로 로그인 페이지로 리다이렉트하고, 모바일은
  `401 JSON`으로 응답한다.

### 결정 (Decision)

**클라이언트 종류와 무관하게 동일하게 `401 Unauthorized`로 응답한다.**

이유는 다음과 같다.

1. [결정 3](#3-웹모바일-공통-인증-처리--인터셉터--argumentresolver)에서 웹/모바일 통합
   방식을 선택했으므로, 인증 실패 응답도 동일하게 처리하는 것이 일관성 있다.
2. 웹의 경우에도 서버가 직접 리다이렉트하지 않고, `401`을 받은 프론트엔드가 로그인
   페이지로 이동시키면 되므로 굳이 클라이언트별로 응답을 분리할 필요가 없다고 판단했다.

구현상 인증 실패는 `UnauthorizedException`으로 던져지고, `GlobalExceptionHandler`가
이를 일관된 `401` JSON(`GlobalErrorResponse`)으로 변환한다.

### 결과 (Consequences)

긍정적

- 모든 클라이언트가 동일한 형식의 인증 실패 응답을 받아 처리 규약이 단순하다.
- 서버는 응답 분기 로직 없이 한 가지 응답만 책임진다.

부정적 / 트레이드오프

- 웹과 모바일의 인증 실패 시 UX가 달라질 수 있다. 웹은 로그인 페이지로 자동
  리다이렉트되는 것이 사용자 경험상 자연스럽지만, 서버가 `401`만 내려주므로
  프론트엔드가 별도로 리다이렉트 처리를 구현해야 한다.
