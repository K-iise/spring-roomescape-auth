# 3단계 ADR — 인가 (매장 매니저)

> 3단계(인가)에서 내린 아키텍처 결정을 누적 기록한다.
> 핵심 질문은 "인가 판단을 어디에 두고, 어떤 정보로 권한을 확인할 것인가"이며,
> 각 결정은 *왜 그 계층에서 판단했고, 요구사항이 바뀌면 어디가 흔들리는가*를 함께 적는다.

## 배경

예약 서비스는 여러 매장을 지원하고, 각 매장에는 매니저가 있다. 매니저는 자기 매장의
예약만 관리할 수 있어야 하며, 다른 매장의 예약은 변경·삭제할 수 없다. 즉 인증
(2단계)만으로는 부족하고, "로그인한 매니저가 이 예약을 만질 권한이 있는가"라는 인가가
필요하다.

전제로, 현재 도메인에는 매장·매니저 개념이 없다(`member`에 역할 컬럼 없음). 또한 이미
사용자 예약에는 **소유자 기반 인가**가 존재한다 — `Reservation.validateOwner(memberId)`를
서비스가 호출하고 실패 시 403(`ForbiddenException`). 3단계는 이 패턴을 *소유자 기준*에서
*매장 기준*으로 한 겹 확장하는 일이다.

## 1. 매장·테마·예약 모델링

- 상태: 채택 (Accepted)
- 일자: 2026-06-17

### 맥락 (Context)

매니저 인가의 모든 판단은 "이 예약이 어느 매장 소속인가"에서 출발한다. 그러려면
매장을 어떻게 표현하고 예약과 어떻게 연결할지 먼저 정해야 한다.

- 새 `store` 엔티티 + `theme.store_id`: 한 매장이 여러 테마(방)를 소유. 예약은 기존
  `theme_id`로 매장까지 도달한다.
- 예약에 `store_id` 직접: 인가 비교 쿼리는 단순하나 매장 정보가 예약에 비정규화된다.
- 기존 `theme`를 매장으로 간주: 새 엔티티는 없으나 "지점 = 방"이 되어 의미가 거칠다.

### 결정 (Decision)

**`store(id, name, manager_member_id)` 엔티티를 새로 두고, `theme.store_id`로 테마가
매장에 속하게 한다.** 예약은 기존 구조(`reservation.theme_id`)를 그대로 두고, 예약 →
테마 → 매장 경로로 소속 매장을 도출한다.

방탈출 도메인에서 한 매장(지점)이 여러 테마(방)를 보유하는 구조가 자연스럽고,
`reservation` 스키마를 바꾸지 않아 기존 예약 흐름·데이터에 영향이 없다.

### 결과 (Consequences)

긍정적

- 예약 스키마 변경이 없어 기존 기능·테스트에 파급이 없다.
- 매장이 테마를 소유하는 현실적 구조를 그대로 표현한다.

부정적 / 트레이드오프

- 예약의 소속 매장을 알려면 테마를 거쳐야 한다(조인 한 단계).

흔들림

- "테마가 여러 매장에 공유된다" 같은 변화가 오면 `theme.store_id` 단일 FK로는
  부족해지고, 예약-매장 연결 방식을 재검토해야 한다.

## 2. 인가 판단 위치 — 도메인 규칙 + 서비스 호출

- 상태: 채택 (Accepted)
- 일자: 2026-06-17

### 맥락 (Context)

"자기 매장 예약만 관리"라는 규칙을 코드 어디에 둘지 정해야 한다. 구현 조건은
인가 판단이 컨트롤러에 과도하게 흩어지지 않을 것을 요구한다.

- 컨트롤러에서 선제 차단: 규칙이 컨트롤러마다 흩어지고 테스트가 어렵다.
- 서비스에서만 비교: 단순하지만 규칙의 재사용·표현력이 떨어진다.
- 도메인 규칙 + 서비스 호출: 규칙은 도메인이 갖고, 서비스가 호출한다.

### 결정 (Decision)

**도메인 객체가 인가 규칙을 갖고, 서비스가 이를 호출한다.** 기존
`Reservation.validateOwner(memberId)` 패턴을 그대로 이어, `Reservation.validateManagedBy(store)`
형태로 "이 예약을 이 매장이 관리할 수 있는가"를 도메인에서 판단하고 위반 시 403을 던진다.
서비스는 "언제 검증할지"(조회 후, 변경·삭제 전)를 책임진다.

### 결과 (Consequences)

긍정적

- 권한 규칙이 도메인 한 곳에 모여 컨트롤러에 흩어지지 않는다(구현 조건 충족).
- 기존 소유자 인가와 동일한 패턴이라 일관성·가독성이 좋다.

부정적 / 트레이드오프

- 도메인이 판단하려면 비교 대상(매장 등)을 인자로 받아야 하므로, 서비스가 필요한
  정보를 먼저 조회해 넘겨야 한다.

흔들림

- "여러 매장 관리"(1:N)나 규칙 변경이 와도 도메인 메서드만 바뀌고 호출부는 그대로다.

## 3. 매니저·매장 관계 — 1:1

- 상태: 채택 (Accepted)
- 일자: 2026-06-17

### 맥락 (Context)

한 매니저가 하나의 매장만 관리하게 할지, 여러 매장을 관리할 수 있게 열어둘지 정한다.
또한 "매니저인지" 여부를 어떻게 식별할지도 함께 결정해야 한다.

### 결정 (Decision)

**매니저와 매장은 1:1로 둔다.** `store.manager_member_id`로 매장이 매니저를 가리킨다.
별도의 `role` 컬럼 없이, **어떤 매장의 `manager_member_id`로 등록되어 있으면 매니저**로
도출한다(`store.manager_member_id = loginId` 조회).

현재 요구는 "자기 매장"(단수)뿐이므로 1:N은 불필요한 복잡도다. 단, 인가 판단을
도메인 메서드([결정 2](#2-인가-판단-위치--도메인-규칙--서비스-호출))로 두었기 때문에
1:N으로 확장하더라도 도메인·매핑만 바뀐다.

### 결과 (Consequences)

긍정적

- 모델이 단순하고, 역할 컬럼 없이 매니저 식별이 가능하다.

부정적 / 트레이드오프

- 한 사람이 여러 매장을 관리하는 요구가 생기면 매핑 구조를 바꿔야 한다.

흔들림

- 1:N 전환 시: `manager_store` 매핑 테이블 + 도메인 규칙(`관리 매장에 포함되는가`)만
  변경되고, 컨트롤러/서비스 호출 형태는 유지된다.

## 4. 권한 확인 방식 — 조회 후 비교

- 상태: 채택 (Accepted)
- 일자: 2026-06-17

### 맥락 (Context)

단건(변경·삭제) 요청에서 권한을 어떻게 확인할지 정한다.

- 조회 후 비교: 예약을 먼저 조회한 뒤 소속 매장을 비교한다.
- 권한 조건 포함 조회: 처음부터 `WHERE store_id = 내매장` 조건으로 조회한다.

### 결정 (Decision)

**예약을 먼저 조회하고(없으면 404), 그 예약의 소속 매장과 매니저의 매장을 비교한다.**
이 방식은 "리소스가 없음(404)"과 "리소스는 있으나 권한 없음(403)"을 명확히 구분할 수
있어, 인증 실패와 인가 실패를 구분하라는 요구([결정 5](#5-인가-실패-응답--403404-구분))와
맞물린다.

> 목록 조회는 예외다. "자기 매장 예약 목록"은 처음부터 매장 범위로 조회한다
> (전체를 가져와 필터링하지 않는다). 조회 후 비교는 단건 접근에 적용한다.

### 결과 (Consequences)

긍정적

- 404/403을 또렷하게 구분해 응답할 수 있다.

부정적 / 트레이드오프

- 다른 매장 예약이라도 "존재한다"는 사실이 403을 통해 드러난다(리소스 존재 노출).

흔들림

- 존재 자체를 숨겨야 하는 보안 요구가 생기면 [결정 5](#5-인가-실패-응답--403404-구분)와
  함께 "권한 조건 포함 조회 + 404"로 바꾼다.

## 5. 인가 실패 응답 — 403/404 구분

- 상태: 채택 (Accepted) — 2단계 ADR [결정 5. 인증 실패 응답(401)](./0002-step2.md#5-인증-실패-응답--웹모바일-동일-401)과 구분된다.
- 일자: 2026-06-17

### 맥락 (Context)

권한 없는 접근에 대해 "권한 없음(403)"으로 응답할지, "리소스 없음(404)"으로 숨길지
정한다. 더불어 미인증(401)과도 뭉개지지 않아야 한다.

### 결정 (Decision)

**세 가지 실패를 구분한다.**

- 로그인하지 않음 → **401** (2단계의 인증 실패, `UnauthorizedException`)
- 로그인했으나 매니저가 아니거나 다른 매장 예약 → **403** (`ForbiddenException`)
- 대상 예약이 존재하지 않음 → **404** (`NotFoundException`)

요구사항이 인증 실패와 인가 실패를 구분하라고 명시하므로, 이미 존재하는
`ForbiddenException`(소유자 인가에서 쓰던 403)을 매장 인가에도 재사용해 일관되게 처리한다.

### 결과 (Consequences)

긍정적

- 클라이언트가 "로그인하라(401) / 권한이 없다(403) / 없는 리소스다(404)"를 구분해
  대응할 수 있다. 기존 예외·상태 매핑(`GlobalExceptionHandler`)을 그대로 활용한다.

부정적 / 트레이드오프

- 403은 다른 매장 예약의 존재를 노출한다([결정 4](#4-권한-확인-방식--조회-후-비교) 참조).

흔들림

- 응답 정책이 바뀌어도 예외 → 상태 매핑 한 곳(`GlobalExceptionHandler`)만 손대면 된다.

## 6. 인증 정보와 도메인 정보의 연결

- 상태: 채택 (Accepted) — 2단계 ADR [결정 1](./0002-step2.md#1-jwt-토큰-기반-인증으로-전환)의 "토큰에는 식별자만" 원칙을 잇는다.
- 일자: 2026-06-17

### 맥락 (Context)

매니저의 매장 정보를 어디서 얻을지 정한다. 로그인 식별자로 매번 조회할지, 토큰/로그인
객체에 매장 정보까지 담을지의 선택이다.

### 결정 (Decision)

**로그인 식별자(`memberId`)로 매장을 서버에서 조회한다.** 토큰과 `LoginMember`에는
매장 정보를 넣지 않는다.

2단계에서 "토큰에는 식별자만 담고, 이름·권한 등은 매 요청 시 서버가 조회한다"를 원칙으로
세웠다(`LoginMemberArgumentResolver`). 매장 정보를 토큰에 박으면 매니저의 매장이 바뀔 때
토큰이 stale해진다. 같은 원칙을 유지해 권한의 원천을 항상 DB로 둔다.

### 결과 (Consequences)

긍정적

- 매장 이동·권한 변경이 다음 요청에 즉시 반영된다(토큰 재발급 불필요).
- 2단계 인증 설계와 일관된다.

부정적 / 트레이드오프

- 매니저 요청마다 매장 조회가 한 번 더 발생한다.

흔들림

- 조회 비용이 문제가 되면 캐싱을 도입하되, 권한 원천이 DB라는 점은 유지한다.

## 7. 매니저 작업 엔드포인트 분리

- 상태: 채택 (Accepted)
- 일자: 2026-06-17

### 맥락 (Context)

매니저의 "자기 매장 예약 조회·변경·삭제"를 어느 엔드포인트에 둘지 정한다. 사용자
`/reservations`는 소유자 인가로 동작 중이고, `/admin/reservations`는 현재 검증 없는
강제 삭제만 있다.

- 사용자 엔드포인트에서 역할 분기(소유자면 자기 예약, 매니저면 자기 매장).
- 매니저 전용(관리자) 엔드포인트 분리.

### 결정 (Decision)

**매니저 작업은 `/admin/reservations`(관리자 영역)에 둔다.** 이 영역을 매니저 전용으로
재정의해 조회(자기 매장 목록)·변경·삭제에 매장 인가를 적용한다. 사용자 `/reservations`는
소유자 인가 그대로 유지한다. 매니저로 등록된 매장이 없는 사용자가 접근하면 403이다.

같은 자원이라도 목적이 다르면 분리한다는 프로젝트 원칙에 따라, 소유자 인가와 매장 인가가
한 메서드에 뒤섞이지 않도록 엔드포인트를 나눈다.

### 결과 (Consequences)

긍정적

- 소유자 인가와 매장 인가가 서로 얽히지 않아 각 컨트롤러/서비스 흐름이 단순하다.
- 사용자/관리자 API 분리 원칙과 일관된다.

부정적 / 트레이드오프

- 예약 변경·삭제 로직 일부가 사용자/매니저 흐름에 나뉘어 존재한다(승격 등 공통 로직은
  재사용하되 진입점이 둘이 된다).

흔들림

- 매니저 권한의 적용 대상(예: 시간·테마 관리까지)이 늘어나면 같은 패턴으로 관리자 영역에
  엔드포인트를 추가한다.
