## 1. 세션 기반 인증 채택

- 상태: 채택 (Accepted)
- 일자: 2026-06-16

### 맥락 (Context)

방탈출 예약 시스템에 로그인/인증 기능을 도입한다. 로그인에 성공한 사용자를
이후 요청에서 **서버가 동일한 사용자로 식별**할 수 있어야 하며, 예약 생성·취소는
요청 본문의 이름이 아니라 **인증된 사용자**를 기준으로 동작해야 한다.

인증 정보를 어떻게 발급하고 검증할지에 대해 크게 두 가지 선택지가 있다.

- **세션 기반 인증**: 서버가 세션을 생성하고 사용자 식별자를 세션에 저장한다.
  클라이언트는 세션 ID(쿠키)만 들고 다니며, 서버가 상태를 보관한다.
- **토큰 기반 인증(JWT 등)**: 서버가 서명된 토큰을 발급하고, 요청마다 토큰을
  검증한다. 서버는 인증 상태를 보관하지 않는다(무상태, Stateless).

> 참고: `build.gradle`에 `jjwt` 의존성이 존재하지만 현재 사용하지 않는다.
> 토큰 기반으로의 전환 여지를 열어 두기 위한 것이며, 이 결정으로 제거하지 않는다.

### 결정 (Decision)

**세션 기반 인증을 채택한다.**

이유는 다음과 같다.

1. **서버가 로그인 상태를 직접 관리**할 수 있어 로그아웃 및 권한 관리가 용이하다.
   세션을 무효화하면 즉시 로그인 상태를 종료할 수 있다.
2. 현재 프로젝트는 **단일 서버 환경**으로 운영된다. 따라서 토큰 기반 인증이
   제공하는 무상태성(Stateless)이나 서버 간 인증 정보 공유와 같은 장점을 적극적으로
   활용할 상황이 아니라고 판단했다.

### 결과 (Consequences)

긍정적

- 로그아웃·강제 만료 등 인증 상태 제어가 단순하고 직관적이다.
- 클라이언트는 토큰을 직접 다루지 않으며, 쿠키 기반으로 처리가 간단하다.

부정적 / 트레이드오프

- 서버가 세션 상태를 보관하므로 **수평 확장 시 세션 공유 문제**가 생긴다.
  (스티키 세션, 외부 세션 저장소 등 추가 장치 필요)
- 서버 메모리에 세션이 쌓인다.

재검토 조건

- 서버를 다중 인스턴스로 확장하거나, 외부 클라이언트(모바일 등)에 인증을 개방해야
  하는 요구가 생기면 토큰 기반 인증으로의 전환을 다시 검토한다. 이미 추가된
  `jjwt` 의존성을 활용할 수 있다.

## 2. 공통 처리 방식 — 인터셉터 + ArgumentResolver

- 상태: 채택 (Accepted)
- 일자: 2026-06-16

### 맥락 (Context)

세션 기반 인증([결정 1](#1-세션-기반-인증-채택))을 도입하면서, 인증이 필요한 API에서
두 가지 공통 관심사를 처리해야 한다.

1. **인증 여부 검증** — 로그인하지 않은 요청을 일관되게 401로 차단한다.
2. **로그인 사용자 식별** — 예약·대기의 주체를 요청 본문이 아니라 세션에서 도출한다.
   (클라이언트가 보낸 이름을 신뢰하지 않는다.)

이를 각 컨트롤러에서 직접 `HttpSession`을 꺼내 처리하면, 동일한 로직이
컨트롤러마다 반복되고 빠뜨리기 쉽다. 공통 지점에서 한 번에 처리할 방법이 필요하다.

고려한 선택지는 다음과 같다.

- **각 컨트롤러에서 직접 처리**: `HttpServletRequest`/`HttpSession`을 파라미터로 받아
  매번 검증·조회. 단순하지만 중복되고 누락 위험이 크다.
- **인터셉터 + ArgumentResolver**: 인증 검증은 `HandlerInterceptor`로, 사용자 주입은
  `HandlerMethodArgumentResolver`로 분리해 공통화한다.
- **Spring Security**: 표준 보안 프레임워크. 기능은 강력하나 현재 요구사항 대비
  학습·설정 비용이 크고, 단계 학습 목표(직접 구현)와 맞지 않는다.

### 결정 (Decision)

**인터셉터로 사용자를 검증하고, ArgumentResolver에서 로그인 멤버 정보를 제공한다.**

- `AuthInterceptor`(`HandlerInterceptor`)에서 세션의 로그인 여부를 검증한다.
  미인증 요청은 `UnauthorizedException`으로 일관된 **401** 응답을 반환한다.
  인증이 필요한 경로(`/reservations`, `/waitings`)에만 등록하여 인증 필요/불필요
  API를 구분한다.
- `LoginMemberArgumentResolver`(`HandlerMethodArgumentResolver`)에서 세션의
  회원 식별자로 회원을 조회해 `@Login LoginMember` 파라미터로 주입한다.
  컨트롤러는 세션 접근 코드 없이 로그인 사용자를 받아 사용한다.

두 책임을 분리한 이유는, **차단(검증)** 과 **주입(식별 정보 제공)** 은 관심사가
다르기 때문이다. 검증은 요청 진입 시점에 한 번 막으면 되고, 사용자 주입은 해당
정보가 실제로 필요한 핸들러에서만 일어나면 된다.

### 결과 (Consequences)

긍정적

- 로그인 검증 로직이 인터셉터 한 곳에 모여 컨트롤러마다 반복되지 않는다.
- 컨트롤러는 `HttpSession`을 직접 다루지 않아 테스트·가독성이 좋아진다.
- 인증 주체가 세션에서 도출되므로 요청 본문의 이름을 신뢰하지 않는다.

부정적 / 트레이드오프

- 검증(인터셉터)과 식별(리졸버)이 각각 세션 키(`SessionConst.MEMBER_ID`)에
  의존한다. 키가 어긋나면 동작이 조용히 깨지므로 **상수로 공유**해 일치시킨다.
- 인터셉터 경로 패턴과 `@Login`을 사용하는 핸들러가 별도로 관리된다. 보호가 필요한
  새 엔드포인트를 추가할 때 경로 등록을 누락하지 않도록 주의해야 한다.
